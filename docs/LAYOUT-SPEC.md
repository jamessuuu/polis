# Polis — layout and composition spec

Written 2026-09-06 by a ui-designer pass, downstream of `STRATEGY.md` (binds),
`RENDER-BUDGET.md` (renderer + element budget, unchanged by this spec),
`DESIGN.md` and `CHARACTERS.md` (art direction and character kit — this spec
touches neither the palette nor the figure geometry, only where and how big
things sit on screen). Where a number below conflicts with those documents,
those documents win on palette/lighting/character geometry; this one owns
layout, grid, breakpoints, and the label/camera systems.

**Scope discipline, stated once:** this is a layout and composition fix. It
adds zero entities, invents zero data, and does not touch `iso.mjs`'s
geometry math, the palette, or the character kit. Every number cited below
was either read directly from `site/*.mjs` or computed by running
`computeCity()` against the real `data/ecosystem.json` on this machine today
(2026-09-06) — flagged **[measured]** — or is a recommended starting value
for the implementer to tune against the acceptance test named alongside it —
flagged **[reasoned, gate with a test]**. Nothing here is asserted as a final
production pixel value without a test that can catch drift as the roster
grows toward ~90.

## 0. Diagnosis, in one table

| # | Problem | Root cause found in code | Fix class |
|---|---|---|---|
| 1 | Label collision | `placePlates()` in `city-view.mjs` only ever moves a plate in **+Y** (vertical lift, 26 tries max); it never moves horizontally. Separately, `mountNamePlate()` positions every director/citizen name plate at a fixed offset directly above its building apex with **zero collision awareness** of anything — not other name plates, not district plates. Two disconnected systems, one of which has no collision logic at all. | Unify into one placement pass, add a horizontal search axis, add priority tiers |
| 2 | Composition | `index.html`'s DOM order is status-board → filters(hidden) → **map(hidden)** → list(hidden) → static-roster. The map section starts `hidden` and is revealed by JS after fetch, but its *position* in the DOM is after the status board regardless. `#city-map{width:100%;height:auto;min-width:640px}` ties the map's on-screen height to its *aspect ratio*, not the viewport, so a wide, short isometric scene renders small no matter where it sits. | Reorder the DOM, decouple map height from aspect ratio, collapse the 22,000px roster |
| 3 | Character scale | Figures are already 22 world-units tall (`city-view.mjs`'s `BODY`/head geometry — this was already fixed per `CHARACTERS.md` item 1). The failure is entirely downstream: the SVG's intrinsic `viewBox` is always set to the **whole city's bounds** (`screenBounds()` over all plots), and `preserveAspectRatio="xMidYMid meet"` maps that fixed-size box into whatever CSS container it's given. On a 358px-wide phone frame this yields ≈0.15 px/unit even before camera zoom, and the interactive zoom clamp (`MAX_K = 3.4`) cannot make up a 6-7x deficit. Container size and default framing are the whole problem. | A per-breakpoint "focus frame" (a second, smaller `viewBox`) for the default view; camera zoom (`MIN_K`/`MAX_K`, unchanged) still governs interaction from there |

None of the three fixes below change `DESIGN.md`'s palette or lighting, or
`CHARACTERS.md`'s figure geometry, insignia, or attribute mapping. None
change `MIN_K`/`MAX_K` (0.55 / 3.4) as endorsed in `DESIGN.md` §7 — that
clamp stays exactly as documented; problem 3 is solved by changing *what the
camera's k=1 reference frame is*, not the clamp around it.

## 1. Composition — the reordered page

### 1.1 Page order, JS-enhanced (all breakpoints)

1. Skip link (unchanged)
2. `<header class="site-header">` — unchanged content, tightened vertical
   padding at `<600px` (see §2)
3. **NEW — headline strip.** One line, generated by `bin/build-site.mjs` from
   the same data as the findings section (never hand-authored — see §1.6).
   Sits between the header and the map on every breakpoint.
4. **HERO — `#map-section`**, moved up from its current position (was:
   after filters/status, before the list). Full-bleed width, explicit
   viewport-relative height (§1.4). Toolbar, city, legend — unchanged
   internals.
5. **NEW — `#findings-section`.** The two (see §1.6, reserve a slot for a
   third) `.finding` blocks, un-nested from the status board and given their
   own section, immediately below the hero.
6. **`#status-board`**, demoted. Same generated `stats-grid`, now supporting
   detail rather than the first thing on the page.
7. **`#filters-section`** + **`#list-section`** (interactive roster),
   collapsed by district by default (§1.7).
8. `#citizen-panel` (aside; unaffected — it is positioned independently of
   document flow and opens on selection regardless of where the map sits in
   the DOM).
9. `#static-roster-section` (no-JS fallback; unaffected in *content*,
   collapsed by district — §1.7).
10. `<footer>` (unchanged).

### 1.2 Page order, JS off

`#filters-section`, `#map-section`, `#list-section` keep the `hidden`
attribute they already have in raw HTML and are never revealed — this is
existing, unaffected behaviour (`app.mjs` only removes `hidden` after a
successful fetch). Moving `#map-section` earlier in the DOM costs a no-JS
visitor nothing: it is invisible in both the old and new position. The no-JS
reading order becomes:

header → headline strip → findings-section → status-board →
static-roster-section (collapsed) → footer.

This is a **strict improvement** over today's no-JS order (header → status
board with findings buried inside it → static roster): the two findings that
STRATEGY §2 calls "the finding that makes it worth a share" now lead, for
every visitor, JS or not. That is a deliberate, positive side effect, not
just a JS-only cosmetic reorder.

### 1.3 Why reorder the DOM instead of using CSS `order`

Rejected: using flexbox/grid `order` to visually promote the hero while
leaving it later in DOM/tab order. `order` decouples visual sequence from
focus and reading sequence (a real WCAG 1.3.2 / 2.4.3 risk), and the map
section carries interactive controls (toolbar buttons) that a sighted
keyboard user would then reach in a different order than they see them.
Physically moving the section is free here specifically because it starts
`hidden` — there is no equivalent no-JS regression to trade against.

### 1.4 The hero: full-bleed, taller, not sticky

**Full-bleed: yes**, extending the existing breakout technique already used
by `.map-scroll` (`width: min(100vw - 2rem, 1480px)` + `margin-left:50%;
transform:translateX(-50%)`, documented in `styles.css` as a deliberate fix
for centering against the parent rather than the viewport). Extend the same
mechanism, don't invent a new one:

```
.hero-map {
  width: min(100vw, 1800px);   /* was: min(100vw - 2rem, 1480px) */
  margin-left: 50%;
  transform: translateX(-50%);
}
```

The 1800px cap exists for the same reason `RENDER-BUDGET.md` and `DESIGN.md`
already reason about scale: a single fixed-camera isometric diorama
stretched to a 3440px ultrawide is "just stretching it," not craft (general
doctrine: verify tablet/desktop don't just scale the phone layout). Below
1800px viewport width (everything at 390/768/1440) the cap never engages —
`min(100vw, 1800px)` is `100vw` at all three tested widths.

**Taller: yes**, and this is the load-bearing change. Replace
`#city-map{width:100%;height:auto;min-width:640px}` — the `min-width:640px`
rule is the exact, named mechanism behind "at 390px the map renders at 640px
inside a 358px frame" — with an explicit, viewport-relative height on the
container, and `height:100%` (not `auto`) on the SVG:

| Breakpoint (container width) | `.hero-map` height | `min-height` |
|---|---|---|
| `<600px` (390 tested) | `min(64vh, 560px)` | `420px` |
| `600–1023px` (768 tested) | `min(72vh, 640px)` | `480px` |
| `>=1024px` (1440 tested) | `min(78vh, 760px)` | `560px` |

`preserveAspectRatio="xMidYMid meet"` (unchanged) letterboxes into whichever
dimension isn't binding; the sky rect (already sized to 3x the view box,
unchanged) fills any letterbox space, so there is never a hard-edged empty
bar — it reads as more sky, which `DESIGN.md` §1 already licenses as craft.

**Sticky: no.** Rejected. Three reasons: (1) not required by any STRATEGY
state — the brief's five states are about what's *visible*, never about
persistence across scroll; (2) it works against the "reads at rest, a single
static frame" requirement (§3.5) by turning the hero into a continuously
present chrome element, which drifts toward the "dashboard with sparkles" /
HUD-over-a-chart fail condition (§6, fail condition 6) the brief explicitly
names; (3) a sticky SVG with an internal keyboard-pannable `tabindex="0"`
map creates a scroll-trap risk for keyboard users scrolling past it. Full
stop in normal flow, tall and first, is the whole fix.

### 1.5 The headline strip (new, small)

One line, sitting between the header and the hero, on **every** breakpoint
(not mobile-only — consistency across breakpoints is the point, and it is
what guarantees the 390px "one headline finding" requirement without any
special-casing). Reuses the existing `.finding` component's visual language
rather than inventing a new one:

```html
<p class="finding finding-strip">
  <strong class="finding-strip-count">8</strong>
  of 59 citizens are named by no charter, upstream or downstream.
  <a href="#findings-section">See the findings ↓</a>
</p>
```

- `.finding-strip-count` reuses the `.stats-grid dd` type role: `--font-mono`,
  weight 600, sized at the H3 role (1.125rem) rather than the stat-grid's
  1.80rem — a strip is a sentence, not a card.
- Padding: `--space-3 --space-4` (see §2.1 for the token set this spec
  introduces).
- **Generation rule, non-negotiable per STRATEGY §6 and §4.1's recorded
  failure:** the count and the sentence fragment are emitted by
  `bin/build-site.mjs` from the same pass that renders `#findings-section`,
  reading whichever `.finding` block is first in the generated list — never
  a second, independently hand-typed number. This is exactly the mechanism
  that broke `polis-sigma.vercel.app` (stale, hand-authored status board);
  the fix is "one generator, two render targets," not "two authors."
- If a third finding (see §1.6 note) is added and reordered to be most
  severe, the strip automatically reflects it — it has no hardcoded
  knowledge of which finding is "the" headline, only "the first one."

### 1.6 Findings surface, promoted

`#findings-section` holds the `.finding` and `.finding-warn` blocks
unchanged in markup/content, simply moved out of `#status-board` into their
own `<section aria-labelledby="findings-heading">`, directly below the hero.

**Open item, flagged not fixed:** `STRATEGY.md` §2 names "33 of 59 never
dispatched" as *the* finding worth sharing, alongside the existing
"8 unreachable" and "2 withheld." No `.finding` block for the dispatch
number exists in `index.html` today — this is a data/content gap
(`bin/build-site.mjs` would need to derive it from `workforce.json`, which
is already fetched for the walker system), not a layout gap. This spec
reserves the pattern for it: `#findings-section` is built to hold **N**
`.finding` blocks generically (CSS: block-level stack, `gap: --space-4`,
no assumption of exactly two), so a third block can be added by whoever
owns the data derivation (chief-of-staff/architect call, not mine) without
any layout rework. Noted as an open question in §9.

Layout:
- `<1024px`: single column, full width of `.page` (unchanged 1180px
  column — **the findings/status/roster area does not break out full-bleed;
  only the hero does**, so reading measure stays inside the existing 66ch
  paragraph rule).
- `>=1024px`: two-column grid alongside the status board —
  `grid-template-columns: 1.6fr 1fr; gap: --space-8` — findings wider/left
  (more important), stats-grid narrower/right (supporting detail). Below
  1024px they stack, findings first.

### 1.7 Status board, demoted

Same generated `dl.stats-grid`, unchanged markup, simply positioned after
`#findings-section` instead of containing it. No visual change beyond
position.

### 1.8 The 22,000px roster — collapse, don't delete

Both surfaces that list all 59 citizens/86 skills — the no-JS
`#static-roster-section` and the JS-built `#list-section`/`#roster-list` —
get the same treatment, because they already share CSS selectors
(`.static-district, .roster-district`) and should stay one visual pattern,
not two (doctrine: reuse, don't invent a second thing that differs for no
reason).

**Mechanism: native `<details>`/`<summary>` per district, collapsed by
default.** Not a JS accordion — a browser-native disclosure widget:

```html
<li class="static-district">
  <details>
    <summary><h3>03 · Engineering <span class="static-count">(15 citizens)</span></h3></summary>
    <ul class="static-agent-list">...</ul>
  </details>
</li>
```

Why this over the task's other candidates (a "show more" button, pagination,
lazy-render):

- **Requires no script.** `<details>` toggles with zero JS, so the no-JS
  fallback stays "complete... with JS off" (STRATEGY §6) by construction —
  every citizen is one click away with no script running at all, which a
  bespoke JS accordion cannot promise.
- **Nothing is removed from the DOM.** Closed content is not `display:none`;
  it is present, and every evergreen browser (Chrome/Edge/Firefox/Safari,
  all shipped this behaviour by 2023) reveals matching text inside a closed
  `<details>` on in-page find (Ctrl+F). Flagged as an item to verify against
  this project's actual supported-browser floor before shipping (§9) —
  cheap to check, not blocking.
- **Zero SVG-budget cost.** This is plain HTML outside the map entirely; it
  does not touch the 2,400-element ceiling at all.
- **The Archive (86 skills)** gets the same treatment, grouped by the six
  guild collections `DESIGN.md` §2.2 already establishes ("the Archive
  becomes a library with six visible collections instead of an 86-box grey
  slab") — one `<details>` per guild collection inside the Archive's own
  `<details>`, so the visual metaphor already chosen for the map's palette
  carries into the text fallback too.

**JS-built roster (`#list-section`) behaviour:** build the same
`<details>`-wrapped groups (a markup change in `app.mjs`'s roster-building
code, not new CSS). One small, scoped behaviour addition: when a filter
(search/district/tool/director) narrows a group to a non-empty match set,
set that group's `open` attribute so filtering still works exactly as today
— collapsed-by-default only applies to the *unfiltered* state. An optional
"Expand all / Collapse all" control above the list is a legitimate small
JS-only enhancement, not required for correctness.

**Height impact (illustrative):** collapsing the roster's ~22,000px down to
8 `<summary>` rows (Districts) + 1 `<summary>` row (Archive) at rest reduces
the collapsed-state page height from ~23,500px to roughly header + headline
strip + hero + findings + status + ~9 summary rows + footer — on the order
of 2,000-2,800px depending on breakpoint, i.e., the roster stops being 97%
of the page by default and becomes reachable, not omnipresent.

## 2. Grid, spacing tokens, type

### 2.1 Spacing tokens (new, scoped to the components this spec touches)

`site/styles.css` has no formal spacing scale today — values are ad hoc rem
figures (0.45, 0.79, 0.89, 1.1, 1.4, 1.8, 2.1...). **Retrofitting the entire
953-line stylesheet onto a formal scale is out of scope for this pass** —
flagged explicitly rather than silently left inconsistent (§9). This spec
introduces a small named scale, values chosen to match rhythm already in use
so adopting them elsewhere later is a rename, not a re-layout:

```css
:root {
  --space-1: 0.25rem;  /* 4px */
  --space-2: 0.5rem;   /* 8px */
  --space-3: 0.75rem;  /* 12px */
  --space-4: 1rem;     /* 16px */
  --space-5: 1.25rem;  /* 20px */
  --space-6: 1.5rem;   /* 24px */
  --space-8: 2rem;     /* 32px */
  --space-10: 2.5rem;  /* 40px */
  --space-11: 2.75rem; /* 44px — names the existing `main section{margin-bottom:2.75rem}` value */
  --space-12: 3rem;    /* 48px */
  --space-16: 4rem;    /* 64px */
}
```

Every spacing value introduced by this spec (headline-strip padding, hero
margins, findings-grid gap) is cited by one of these names, not a raw
number.

### 2.2 Type — reused, nothing new

No new font sizes. Every text role this spec uses already exists:

| Role | Existing rule | Reused for |
|---|---|---|
| H1 | 2.03rem / 620 (`h1`) | Page title, unchanged |
| H2 | 1.42rem / 620, bottom border (`h2`) | Section headings (`findings-heading`, `status-heading`, `static-roster-heading`) |
| H3 | 1.125rem (`h3`) | District `<summary><h3>`, `.finding h3`, headline-strip count size |
| H4 | 1rem / 620 (`h4`) | Citizen name headings inside roster |
| Body | 1rem / 1.55 line-height (`p`) | Prose, finding text |
| Mono-number | `--font-mono`, 600, 1.80rem (`.stats-grid dd`) | Stat numbers, unchanged |
| Mono-label | `--font-mono`, 0.79rem uppercase (`.stats-grid dt`) | Unchanged |

Map/SVG type (world units, from `DESIGN.md` §6, unchanged by this spec):
precinct number/title 27u, precinct sub 19u, name plate 20u, plate padding
12u, plate height 66u, name-plate height 32u.

## 3. Breakpoint behaviour — 390 / 768 / 1440

All three are container-width bands checked against `.hero-map`'s own
`clientWidth` via `ResizeObserver` (not `window` width — the map should
react to the space it's actually given, consistent with "verified at real
widths, not by resizing a window," §6). Bands: `<600px`, `600–1023px`,
`>=1024px` — chosen so all three tested widths (390/768/1440) fall cleanly
inside one band each, with no boundary case at the tested widths themselves.

| | **390px** (band `<600`) | **768px** (band `600–1023`) | **1440px** (band `>=1024`) |
|---|---|---|---|
| Hero width | `100vw` (edge to edge) | `100vw` | `100vw` |
| Hero height | `min(64vh, 560px)` ≈ 540px at 844 tall | `min(72vh, 640px)` | `min(78vh, 760px)` |
| Map default framing | `FOCUS_DISTRICT` (§4) — Cabinet only | `FOCUS_RING` (§4) — Cabinet + nearest neighbours | `FOCUS_CITY` (§4) — whole city, modest crop |
| Headline strip | Visible, 1 line, no scroll needed | Visible, 1 line | Visible, 1 line |
| Findings/status | Below the fold, single column | Below the fold, single column | Below the fold, 2-col grid at `.page` width |
| Roster | Collapsed `<details>`, full width | Collapsed `<details>`, full width | Collapsed `<details>`, 2-col text wrap unaffected |
| Toolbar buttons | Existing global button sizing (`padding:0.45rem 0.7rem`) — clears WCAG 2.5.8 AA's 24px floor; flagged to accessibility-engineer for target-size sign-off, not redesigned here | Same | Same |
| First-screen result | Header + strip + hero visible with **zero scroll** on an 844px-tall viewport (64vh hero ≈540px + header ≈64px + strip ≈44px ≈ 648px, leaving ≈196px which surfaces the top of `#findings-section`'s heading as a scroll affordance) | Header + strip + most of hero visible | Header + strip + hero fully visible, findings one short scroll away |

Nothing here requires JS to degrade gracefully differently per breakpoint —
if JS never runs, none of this table applies (map stays `hidden`
everywhere) and the visitor gets header → strip → findings → status →
collapsed roster on every width, per §1.2.

## 4. Character / building / camera scale

### 4.1 What is already correct (do not touch)

- Figure height: **22 world units**, head apex at y=-22.1 (`city-view.mjs`'s
  `BODY` path + `fig-head` circle, r=2.9) — matches `CHARACTERS.md` §2.2
  exactly. **Already shipped.**
- Building heights: `BASE=20, PER_LINK=4.2, MAX=110, DIRECTOR_BONUS=12`
  (`layout.mjs` `HEIGHTS`) — already the raised set `CHARACTERS.md`'s
  reconciliation note asked for. **Already shipped.**
- `TILE_W=64, TILE_H=32` (`iso.mjs`) — the coordinate system everything else
  is measured in.
- Camera clamp `MIN_K=0.55, MAX_K=3.4` (`city-view.mjs` `attachCamera`) —
  **unchanged by this spec.**

None of these need to move. The defect is entirely in what CSS box and what
`viewBox` those correct numbers get displayed inside.

### 4.2 The mechanism: a per-breakpoint focus frame

The SVG element keeps exactly one `viewBox` attribute at a time, but which
rectangle that attribute holds is no longer always "the whole city." Three
named frames, computed the same way `screenBounds()` already computes the
full-city one, just scoped differently:

1. **`FOCUS_CITY`** — unchanged: `screenBounds()` over every plot plus the
   wall, exactly what renders today. Used at `>=1024px`, and as the
   destination of an explicit "zoom out" action at any width.
2. **`FOCUS_DISTRICT`** — bounding box of the focal district (Cabinet, `00`
   — already `DESIGN.md` §7's stated focal point: "graphite Cabinet with
   chief-of-staff's tower") plus: the tallest building in that plot's full
   extrusion height, headroom for its plate/banner stack, and a small fixed
   lateral margin (in tile units, not pixels) for a sliver of street
   context. Used at `<600px`.
3. **`FOCUS_RING`** — bounding box of Cabinet **union** its *k* nearest
   neighbouring plots by centroid distance, where *k* is chosen live
   (pseudocode below) so the combined box still clears the tablet
   legibility floor. Used at `600–1023px`.

At every breakpoint, the camera's interactive state still resets to
`{x:0, y:0, k:1}` for whichever frame is active — `k=1` in a small frame
already reads big; `MIN_K=0.55`/`MAX_K=3.4` still govern zooming in/out
*from there*, completely unchanged. **This is why no amendment to
`DESIGN.md` §7's camera clamp is needed**: the fix changes the reference
frame the clamp operates on, not the clamp itself.

**Transition rule (motion-safe by construction):** switching frames — on
mount, on a `ResizeObserver`-detected band crossing, or via the "zoom out to
the whole city" control — is a **hard cut**: set `viewBox` and reset the
camera transform in the same tick, no interpolation. This avoids animating
`viewBox` (not an `opacity`/`transform` property, and therefore off-limits
per §6's motion constraint) and needs no `prefers-reduced-motion` branch,
because there is no motion to remove.

**"Reset view" button, redefined:** resets to the *current breakpoint's*
default frame (`FOCUS_DISTRICT`/`FOCUS_RING`/`FOCUS_CITY`), not always
`FOCUS_CITY` as an implicit side effect of today's single-frame design. A
separate, explicitly labelled control ("See the whole city") sets
`FOCUS_CITY` regardless of breakpoint — this is the mobile/tablet visitor's
path to job #2 ("the declared system and the running system are not the
same system") within the brief's 2-minute budget, and it is the natural home
for a short caption: e.g. "8 districts, 59 citizens, 8 with no one to answer
to."

### 4.3 Concrete numbers — measured today, formula for tomorrow

Computed by running `computeCity()` against the live `data/ecosystem.json`
on this machine (script discarded after use; the numbers are the durable
artifact):

| Quantity | Value | Source |
|---|---|---|
| Full-city screen bounds | `minX=-1152, maxX=1088, minY=-656, maxY=464` | **[measured]** `screenBounds()` |
| Full-city viewBox width (`+PAD*2`, `PAD=64`) | **2,368 units** | **[measured]** |
| Cabinet plot | `col=-2, row=-2, cols=5, rows=4` (5 citizens) | **[measured]** |
| Cabinet ground diamond | width 288u, height 144u | **[measured]** via `toScreen` on plot corners |
| Tallest building in Cabinet | chief-of-staff, degree 18, director: **107.6u** | **[measured]** `computeCity().buildings` |
| Tallest building citywide | **110u** (the `HEIGHTS.MAX` cap) | **[measured]** |

**`FOCUS_DISTRICT` illustrative crop** (Cabinet + tallest-building headroom
+ label stack + margin): width ≈360-370u, height ≈360-370u (ground diamond
144u + 107.6u building + ≈100u banner/plate headroom + ≈15u ground
allowance for contact-shadow/character shadow + ≈20-40u lateral margin each
side). At a 358-382px-wide phone hero (today's realistic safe-area frame),
this yields a character height of **≈21-25 CSS px** at the wider margin
estimate, or **≈25-28 CSS px** if the lateral margin is trimmed to ≈16-20u
each side. **Recommendation: tune the margin constant down until the
acceptance test (§4.4) reports ≥24px, and keep ≥28px as the comfortable
target**, not the floor.

**Why 24px, defended:** the figure's head (r=2.9u ≈ 5.8u diameter, ≈26% of
total height) is the smallest legibility-critical part. At 24px total
figure height the head resolves to ≈6.3px diameter — clearly a distinct
circular region, not a single blended pixel, and well above the "roughly
the height of a lowercase letter" failure `CHARACTERS.md` §0 diagnosed at
4.4px. 28px (head ≈7.3px) is the comfortable target where torso/leg
separation also reads at a glance, without requiring the `k>=1.5` LOD-1
threshold that unlocks insignia/instrument detail — that stays an
earn-by-zooming bonus, not the default-view floor.

**`FOCUS_RING` selection rule** (tablet, pseudocode — not hand-computed
here, because the exact adjacent-district coordinates are a function of the
live spiral-placement layout and will shift as the roster grows):

```
frame = boundsOf(Cabinet)
k = 0
while legibilityAt(frame, tabletContainerWidth) > FLOOR_COMFORTABLE (28px)
      and k < MAX_RING_DISTRICTS:
  k += 1
  frame = boundsOf(Cabinet ∪ kNearestPlotsByCentroidDistance(k))
use frame from the last k where legibility >= FLOOR_MIN (24px)
```

This is a small, cheap, deterministic, roster-size-agnostic computation
(≤15 plots today) — the kind of "allocated, not simulated" logic
`layout.mjs`'s own header comment already commits this codebase to.

**`FOCUS_CITY` desktop nudge (optional, not gating):** at `k=1` in
`FOCUS_CITY`, a 1424px-wide 1440px hero yields ≈13-14 CSS px characters —
below the comfortable target but **not gated by STRATEGY §6**, whose hard
floor is stated specifically for "a 390px phone." Recommended, not required:
default desktop camera `k=1.25-1.3` instead of `1.0` (a modest crop, trims
outer margin/haze, not any district), nudging desktop default to ≈17-18px
while a single scroll-zoom to `k>=1.5` (already the existing LOD-1
threshold) comfortably clears 28px+ with full detail. If deprioritized,

## 5. Label placement — priority tiers and the unified pass

### 5.1 What exists, reused not replaced

`placePlates()` already does a real thing worth keeping: deterministic,
depth-ordered, greedy collision placement with a leader-line fallback when a
plate is pushed far from its anchor (`p.displaced`, rendered as a dashed
`.plate-leader` line — already styled, already WCAG-compliant, already
motion-safe). The name-plate pool (`NAME_POOL=24`, pre-mounted once,
repositioned by transform, revealed by opacity — zero DOM nodes created on
hover) is also a correct, budget-conscious primitive. **Neither is replaced.
They are unified and the search axis is extended.**

### 5.2 Priority tiers (as specified)

| Tier | What | Current treatment | New treatment |
|---|---|---|---|
| **T1 — district/guild/archive plate** | 15 boxes today (8 districts + 6 guilds + 1 archive) | Vertical-only lift, own collision pass, unaware of name plates | Same pool, joins the unified pass first (placed first = never moved by anything lower) |
| **T2 — director name** | 7 boxes, always mounted | Fixed offset above apex, **zero collision logic** | Joins the unified pass second; nudged (not hidden) to clear T1 and earlier T2s |
| **T3 — citizen name (hover/focus/select/neighbour/crew)** | Up to `NAME_POOL - 7 = 17` remaining slots | Fixed offset above apex, zero collision logic | Joins the unified pass last; nudged first, **dropped** (unmounted, not overlapped) if the offset budget is exhausted |

Never hidden: T1, T2. Only T3 may be dropped from a given frame, and only
when the collision search genuinely cannot place it — the citizen is never
"gone," only not labelled in that instant; the always-present roster list
and the citizen panel remain the complete record (satisfies "any one thing
on screen can be traced to its record in one interaction," §2).

### 5.3 The unified pass

Runs once per `refreshPlates()` call (on mount, and on every
hover/focus/select change — same call sites as today, no new triggers):

```
candidates = []
candidates += allDistrictAndGuildPlates()        // T1, sorted by depth (existing order)
candidates += allDirectorNamePlates()            // T2, sorted by depth
candidates += currentCitizenNamePlates(anchors, neighbours)  // T3, existing NAME_POOL budget logic, sorted by depth

placed = []
for c in candidates:                             // priority order IS placement order
  offsets = [ (0,0) ]
  for dy in [28, 56, 84, ... up to existing try budget]:
    offsets += [ (0,-dy), (-0.4*c.w,-dy), (+0.4*c.w,-dy) ]   // NEW: horizontal member added at each vertical step
  for (dx,dy) in offsets:
    candidate_box = c.naturalBox.offsetBy(dx,dy)
    if no collision with `placed`:
      c.finalBox = candidate_box
      c.displaced = (dx,dy) != (0,0)
      placed.push(c)
      break
  else:
    if c.tier == T3: drop(c)          // never drawn this frame
    else: applyDensityFallback(c)     // §5.4 — T1/T2 never simply overlap
```

The single change that fixes the reported "05 · Growth & Revenue overlaps
01 · Intelligence" defect is the `(-0.4*c.w, -dy)` / `(+0.4*c.w, -dy)`
horizontal members added to the search at every vertical step — two
plates at similar depth (similar row) that vertical-only lift can never
separate (both keep landing at the same height, still overlapping) can now
step sideways instead. The same extension is what lets a director's name
plate step around a district plate it currently sits on top of.

Every candidate whose final `(dx,dy) != (0,0)` draws the existing
`.plate-leader` line style — extended from T1-only to all three tiers. This
is the only new SVG geometry this spec introduces (§7).

### 5.4 Density fallback (T1/T2 only, reserved for future roster growth)

Not expected to trigger at today's 8-district/7-director count, but named
so it exists before the roster reaches ~90 and a denser layout needs it:
when a T1 plate exhausts its offset budget, degrade it to **numeral-chip
only** — reuse the plan numeral already drawn into the district's ground
plane (`DESIGN.md` §4, existing element, not new) at slightly higher
opacity/weight, and suppress the full title/plate. The full plate (already
built, just toggled) reappears on hover/focus of that district or any
citizen inside it — an on-demand disclosure using the exact mechanism
citizen names already use, not a new one. A T2 (director) plate that
exhausts its budget falls back to the same numeral-adjacent tag plus a
single-letter director marker already implied by the mantle geometry — it
is never simply hidden, since "Directors are always named" is a stated page
promise (`DESIGN.md` §6).

> **Overturned 2026-09-07, rendering pass.** The promise was the problem. Seven
> always-mounted director plates were most of the "pile of white boxes" the
> client rejected, and T1's density fallback below is now what a precinct plate
> does (drop the sub-line) while T2 is gated by zoom instead: people are named
> above 1.3x or on interaction, places at every zoom. `DESIGN.md` §6 carries
> the amended promise and the page copy matches it. Nothing became
> unreachable; the roster still names all 59 with JavaScript off.

### 5.5 What this sacrifices

- Simultaneous visibility of **every** neighbour/crew name at once when a
  citizen with many connections is focused, once `NAME_POOL` is exhausted —
  recovered by the fact the roster list and panel already show the complete
  edge list textually regardless of what's labelled on the map.
- Under a much denser future roster, always-on full-text district titles at
  every zoom level — recovered by hover/focus, which is already the pattern
  citizen names use today, so the district treatment becomes consistent
  with the rest of the map rather than a special case.
- Nothing about which entities exist, what they're labelled, or their
  geometry. This section is 100% JS placement logic plus ≤24 new `<line>`
  elements (§7) — no character, building, or data change.
